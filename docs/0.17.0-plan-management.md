# 0.17.0: исполняемые планы ботов

У каждого бота есть один активный план. Модель задаёт программу через JSON-инструменты; игровой поток исполняет её по шагам. Создание, просмотр, отмена, изменение и дополнение работают с тем же деревом и его текущим состоянием. Промежуточные завершения нативных задач привязаны к конкретному запуску через `TaskId` и типизированный `Success`.

## Управление

| Инструмент | Действие |
|---|---|
| `plan(steps=[...])` | Создать или полностью заменить план. Сначала проверяется новое дерево, затем отменяется ожидаемая задача/переход прежнего плана. |
| `inspect_plan()` | Полное JSON-дерево с `plan_id`, `revision`, ID узлов и последовательностей, статусами, аргументами, счётчиками циклов и ожидаемой задачей. План продолжает работать. Результат модель читает следующим ходом. |
| `edit_plan(operations=[...])` | Применить до 16 изменений одной транзакцией. Ошибка любого изменения оставляет прежний план и текущую задачу. |
| `append_plan(steps=[...], node="s0")` | Добавить шаги в конец корневой или выбранной последовательности. Активная задача сохраняется. |
| `update_plan(node="n3", steps=[...])` | Совместимый короткий вариант замены одного узла. |
| `cancel_plan(reason="...", clear_goal=false)` | Отменить остаток плана и принадлежащую ему ожидаемую задачу/временный переход. `clear_goal=true` также снимает цель. Отмена не объявляется успехом. |
| `keep_plan()` | Сохранить выполнение и подтвердить план после обзора. `carry_on` тоже сохраняет активный план. Время, используемое условиями, не обнуляется. |

В изменениях и отмене можно передать `expected_plan_id` и `expected_revision`, взятые из осмотра. Устаревшая версия или другой план отклоняются до изменений. Каждый новый план получает собственный ID, каждая успешная транзакция редактирования — новую ревизию. Неизменённые узлы сохраняют ID.

Операции `edit_plan`:

- `replace`: заменить узел переданными `steps`; пустой список удаляет его содержимое.
- `remove`: удалить узел; поле `steps` отсутствует.
- `insert_before`, `insert_after`: вставить непустой список рядом с узлом в последовательности.
- `append`: добавить непустой список в конец последовательности.
- `prepend`: добавить перед текущей/ожидающей работой выбранной последовательности, не повторяя уже выполненные шаги.

Корень имеет ID `s0`. У веток, тела цикла и блоков обработки ошибок есть собственные ID последовательностей: их показывает `inspect_plan`. Редактирование завершённого/пропущенного узла отклоняется; для дополнительной работы нужно добавить новые шаги или заменить более крупный активный блок. Вставка перед частично выполненным управляющим блоком, которая повторила бы его побочные эффекты, также отклоняется: можно изменить его активную последовательность или конкретный ожидающий шаг.

Замена/удаление активного действия или его предка останавливает связанную задачу. Изменение будущего шага её не останавливает. Уже изготовленные предметы, перемещения и другие завершённые эффекты не откатываются. Постоянные приказы игры остаются отдельным механизмом: `cancel_plan` не снимает их и не отменяет приказы игрока.

Создание, редактирование и отмену нельзя смешивать в одном ответе. Несколько изменений оформляются одним `edit_plan` или совместимыми вызовами редактирования, которые проверяются вместе. С ними допустимы речь, память и осмотры; запускать постороннюю рабочую задачу рядом с `keep_plan` нельзя — новую работу надо добавить в дерево явно.

## Формы узлов

```json
{
  "steps": [
    { "do": "take_item", "args": { "item": "wrench", "count": 1 }, "timeout": 180 },
    {
      "if": "has('wrench')",
      "then": [
        { "do": "repair_systems", "args": {} }
      ],
      "else": [
        { "do": "say", "args": { "text": "Не удалось получить гаечный ключ." } }
      ]
    },
    {
      "try": [
        { "wait_until": "leaks == 0", "timeout": 120 }
      ],
      "catch": [
        { "do": "say", "args": { "text": "Проверю, что мешает закончить работу." } }
      ]
    }
  ]
}
```

Пример показывает форму аргументов `plan`. Идентификаторы предметов, комнат и объектов нужно копировать из текущих наблюдений, включая модовые. Аргументы внутри `do.args` обязаны соответствовать схеме выбранного инструмента; неизвестные поля и неподдерживаемые псевдонимы узлов отклоняются.

Поддерживаются:

- Действие: `{"do":"tool_name","args":{...},"timeout":180}`.
- Ветвление: `{"if":"condition","then":[...],"else":[...]}`; `else` необязательно.
- Ожидание: `{"wait_until":"condition","timeout":60}`.
- Ограниченный цикл: `{"repeat":[...],"until":"condition","max":3}` либо `while` вместо `until`. Без условия выполняется до `max` итераций.
- Обработка ошибки: `{"try":[...],"catch":[...]}`.
- Вложенная последовательность: `{"steps":[...]}`.

`until` проверяется **перед** итерацией и останавливает цикл, когда истинен. `while` тоже проверяется перед итерацией и разрешает выполнение только при истинном условии. Их нельзя указывать одновременно. Достижение `max` завершает ограниченный цикл, но само по себе не доказывает достижение его условия: при необходимости следующая ветка должна проверить результат.

Узлы управления планом нельзя вкладывать в `do`: операции с деревом передаются отдельными инструментами. В осмотре дерево содержит служебные `id/status` и обёртки последовательностей; при создании/редактировании нужны канонические массивы из схемы инструмента, без служебных полей осмотра.

## Условия

Условия — явный язык выражений, а не разбор приказов по словам. Доступны числовые значения, `true`/`false`, сравнения `<`, `<=`, `>`, `>=`, `==`, `!=`, операторы `and`, `or`, `not`, их символьные варианты и скобки. Строковые аргументы функций заключаются в кавычки; кавычки и обратную косую черту можно экранировать.

Числовые факты: `health`, `oxygen`, `room_water`, `room_fire`, `threats`, `leaks`, `flora`, `reactor`, `reactor_fuel`, `sub_oxygen`, `injured`, `time`, `task`, `last_ok`, `last_failed`, `marked`, `bodies`, `free_slots`.

Функции: `in_room('room')`, `has('prefab/#ID')`, `wearing('prefab/#ID')`, `count('prefab/#ID')`, `condition('prefab/#ID')`, `order('id')`, `threat('kind')`, `water('room')`, `fires('room')`, `near('name')`, `result('text')`.

Для инвентаря сервер передаёт отдельные факты `inventoryItems`: каждый реальный предмет, его prefab/ID, состояние, экипировку и расположение, включая содержимое носимых контейнеров. `has`/`wearing` используют точные prefab, ID или имена; `count` считает экземпляры; `condition` возвращает максимальный процент состояния среди совпавших предметов. Достоверно пустой инвентарь отличается от недоступных данных. Старый текстовый поиск `has`/`wearing` остаётся только для совместимости с прежними бэкендами; нативный сервер предоставляет типизированные данные.

Неизвестные имена функций/фактов отклоняются при построении. Недоступные факты во время исполнения не превращаются в выдуманные нули или «полностью безопасное» состояние: вычисляемое условие становится ложным. Булевы операции используют короткое замыкание. Свежие результаты действий и задач сбрасывают кеш наблюдения перед следующими условиями.

`time` — секунды от создания плана. Обзоры, `keep_plan` и добавление шагов его не перезапускают. Успешное ожидание обновляет `last_ok/last_failed/result`, как и обычный шаг.

## Выполнение и границы

Задачи `craft`, `equip`, `drag_body` и остальные действия, возвращающие запуск задачи, ожидают именно своего завершения. Старый отчёт другой задачи не продвигает новый план. Успех/ошибка в нативном бэкенде передаются отдельно от текста: слово `failed` в имени предмета не считается провалом.

Постоянные приказы вроде `fix_leaks`, `follow` и `operate` завершают **шаг выдачи приказа** сразу. Для ожидания фактического результата нужно явно добавить `wait_until` с подходящим условием. Сам приказ выполняется штатным ИИ.

Ожидание условия ограничено 1–300 секундами, по умолчанию 60. У действия можно задать свой `timeout` 1–7200 секунд вне `args`; он применяется к задачам и переходам. Без него задача использует собственный нативный лимит с небольшим запасом, а переход — `planStepTimeoutSeconds`. Ошибки и таймауты переходят в ближайший `catch`; без него остаток плана прекращается с отчётом.

Если отмена задачи по таймауту временно не удалась, план удерживает её ID и повторяет отмену. `catch` и следующие рабочие действия ждут освобождения задачи, чтобы две операции не управляли одним ботом одновременно. Команды игрока из меню обрабатываются раньше готовых ответов модели; ответы, полученные для прежнего приказа или уже удалённого экземпляра агента, отбрасываются.

Нативная задача при ошибке очистки сохраняет владение и повторяет только освобождение своей цели, включая вложенную задачу разбора/крафта. Выполнение самой задачи и одноразовые завершающие действия не повторяются. Итог `salvage + craft` сохраняет признак успеха крафта независимо от текста о разобранных материалах.

Пределы: 40 узлов вместе с последовательностями, глубина 6, 1–10 итераций каждого цикла и 1024 запущенных действия на план. После 16 мгновенных действий выполнение уступает следующему игровому тику. Выражения ограничены 2048 символами, 256 токенами и глубиной 32. Эти границы исключают бесконечный цикл и длительное блокирование игрового потока.

При отключении агента, внутренней ошибке, смене раунда и остановке менеджера ожидаемая задача освобождается. Планы относятся к текущему раунду: старые ID сущностей не переносятся в исполняемое дерево следующего раунда. Долгосрочная память и схема инвентаря сохраняются прежним механизмом.

## Проверка

Тесты проверяют дерево и его атомарные изменения, ID/ревизии, состояния веток и циклов, строгие аргументы, замену текущего действия, сохранение прогресса, корреляцию отчётов, отмену, таймауты с `catch`, свежие факты инвентаря и лимиты исполнения. Интеграционные сценарии проходят через ответы имитатора LLM и тот же менеджер, что используется в игре.

Проверено: **984 теста прошли**, сервер и клиент собраны для Windows/Linux/macOS, симулятор также собирается. В семи сборках нет ошибок и предупреждений компилятора. Проверка зависимостей NuGet в тестовом проекте сообщила о недоступности сети; это не помешало сборке и исполнению тестов из уже восстановленных зависимостей.

Для игрового прогона:

1. Создать план получения инструмента, ремонта и ожидания; проверить порядок действий и живой осмотр дерева.
2. Во время пути добавить хвост, изменить будущую ветку, затем заменить текущую задачу. Проверить отсутствие повторного выполнения законченных шагов и старого продолжения.
3. Отменить перенос тела и крафт; проверить освобождение захвата/резерва и сохранность ранее полученных вещей.
4. Вызвать недоступный материал или путь внутри `try`, проверить переход в `catch`; повторить с таймаутом.
5. Проверить `repeat` с `while`/`until`, изменение фактического количества предметов, достижение лимита и последующую ветку.
6. Изменить план по устаревшей ревизии, отправить неверную вторую операцию в пакете изменений, вставить пустой список перед текущей задачей: прежнее исполнение должно сохраниться.
7. Выдать приказ из меню игрока, отключить бота, сменить раунд и перезагрузить мод: старый план не должен продолжиться.

Игровой прогон этой версии пока не выполнен.
