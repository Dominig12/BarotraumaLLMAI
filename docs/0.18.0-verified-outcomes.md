# 0.18.0: проверка результатов и диагностика задержек

В этой версии шаг плана может отдельно требовать подтверждения результата в игровом мире. Длительное ожидание задачи сопровождается типизированной диагностикой, которую видят LLM и игрок в мониторе ботов.

## Проверка результата шага

У канонического узла `do` появились два необязательных поля:

| Поле | Значение |
|---|---|
| `ensure` | Выражение на существующем DSL условий плана. |
| `verify_timeout` | Сколько секунд ждать подтверждения после успешного действия: 1–300, по умолчанию 10. Требует `ensure`. |

```json
{
  "steps": [
    {
      "try": [
        {
          "do": "equip",
          "args": { "item": "divingsuit" },
          "timeout": 180,
          "ensure": "wearing('divingsuit') and oxygen > 40",
          "verify_timeout": 10
        },
        {
          "do": "go_to_room",
          "args": { "room": "Ballast [h5]" },
          "ensure": "in_room('Ballast [h5]')",
          "verify_timeout": 5
        }
      ],
      "catch": [
        { "do": "say", "args": { "text": "Подготовка не подтверждена. Проверю причину." } }
      ]
    },
    {
      "wait_until": "wearing('divingsuit') and oxygen > 40 and in_room('Ballast [h5]')",
      "timeout": 1
    }
  ]
}
```

Идентификаторы и ссылки в примере необходимо заменить фактическими значениями из наблюдения. Это аргументы инструмента `plan`, а не дополнительные аргументы `equip` или `go_to_room`.

Сначала действие выполняется ровно один раз. После успешного отчёта задачи или прибытия начинается проверка `ensure` по свежему наблюдению. Узел сохраняет ID и получает статус `verifying`; следующие шаги ждут. Как только условие истинно, узел завершается. Истечение `verify_timeout` становится ошибкой шага и использует обычный `catch`; без него план останавливается.

`timeout` ограничивает само действие, `verify_timeout` — последующее подтверждение. Провалившееся действие не превращается в успех даже при истинном `ensure`. Недоступные данные не подтверждают результат. В условии проверки `last_ok` и `result()` относятся к успешному ответу текущего действия, однако текст ответа не следует использовать как доказательство состояния мира.

Для инвентаря доступны `has`, `wearing`, `count`, `condition` и `free_slots`. Они используют реальные `inventoryItems`, в том числе предметы в носимых контейнерах. Условия остаются наблюдениями состояния: `count('bandage') >= 3` подтверждает наличие трёх бинтов, но само по себе не доказывает, что все они изготовлены именно этим действием. Крафт подтверждает производство своей нативной задачей; получение продукции в руки — отдельное действие.

`count` в `take_item`, `move_item` и `loot_body` остаётся верхней границей отбора согласно схеме инструмента. Если поручение требует конкретного минимального запаса, это надо подтвердить через `ensure` с `count(...)`. Успешный `catch` означает выполнение ветки восстановления, а не доказательство исходной цели. В примере финальное ожидание находится снаружи `catch`, поэтому одной реплики об ошибке недостаточно для успешного завершения поручения.

`inspect_plan` показывает `verification_condition`, `verification_native_result`, оставшееся время и полный узел с `ensure`. В мониторе видны проверяемый результат и время ожидания.

Добавление в конец или изменение будущих шагов сохраняет текущую проверку и её срок. Вставка перед проверяемым действием, которая повторила бы его эффект, отклоняется. Явная замена или удаление активного узла отменяет его проверку; изготовленные вещи и другие выполненные эффекты сохраняются. Автоматических повторов действия нет.

## Диагностика задач

`taskProgress` в наблюдении и `task_progress` в осмотре плана содержат:

| Поле | Смысл |
|---|---|
| `taskId` | ID конкретного запуска задачи. |
| `phase` | `running`, `waiting`, `blocked` или `cleanup`. |
| `step` | Описание текущего действия для чтения. |
| `elapsedSeconds` | Длительность задачи. |
| `noProgressSeconds` | Время с последнего измеренного продвижения. |
| `blockerCode`, `blocker` | Стабильный код препятствия и пояснение, если причина известна. |
| `completedUnits`, `totalUnits` | Подтверждённое количество и цель, когда задача умеет их измерять. |

Неизвестные количества отсутствуют. Исполнитель использует типизированные поля; слова в именах предметов и описаниях не управляют диагностикой. Запрос монитора, смена текста стадии или очередной игровой тик не считаются продвижением.

При известном препятствии и отсутствии измеренного продвижения не менее 45 секунд менеджер запрашивает обзор плана. Предупреждение относится только к ожидаемому `taskId`, не отменяет задачу, не увеличивает счётчик её провалов и не запускает действие повторно. Оно не повторяется при неизменном препятствии; новое продвижение позволяет сообщить о следующей задержке. Долгое стационарное действие без известного препятствия не объявляется зависшим только из-за неподвижности бота.

LLM может проверить причину, сохранить полезную работу через `keep_plan`, изменить будущие шаги или явно отменить задачу. Очистка нативной цели сохраняет прежние гарантии владения: новая работа и `catch` ожидают успешного освобождения старой задачи. Бэкенды без диагностики продолжают использовать обычные таймауты.

Обычные осмотры, речь и заметки во время обзора нужно сопровождать `keep_plan`, чтобы сохранить работу. `inspect_plan` сохраняет план самостоятельно. Реализованы коды `machine_busy`, `no_power`, `movement_stalled`, `objective_abandoned`, `native_priority`, `incapacitated` и `cleanup_pending`; неизвестная причина остаётся неизвестной.

## Достоверность нативных результатов

- Передача проверяет фактический конечный инвентарь и заданный слот каждого выбранного предмета. Истории «когда-то положил» недостаточно: исчезнувший или перемещённый предмет делает результат неполным.
- Загрузка через `put_in`, в том числе C4 в снаряд, сверяет присутствие каждого выбранного предмета именно в нужном отделении контейнера. Ранее загруженное, но уже исчезнувшее содержимое не засчитывается как находящееся внутри.
- Перенос предметов в комнату, другому персонажу и в хранилище повторно проверяет текущего владельца или расположение. Подбор и лут проверяют, что полученные вещи всё ещё находятся у бота.
- Крафт считает реальные события создания продукции. Отчёт различает изготовленное, сохранившееся, носимое ботом и оставшееся в машине. Продукция, которую уже использовали или унесли, не объявляется доступной на выходе.
- Разбор подтверждается вызовом нативного `Deconstructor.ProcessItem` для точного предмета и постановкой его на удаление. Внешнее исчезновение и прежняя очередь удаления доказательством не считаются. Выход рецепта не выдаётся за фактическую добычу. Отслеживаются только задачи мода; записи освобождаются при завершении и смене раунда. Если этот перехват недоступен, новая задача разбора отказывается начинать необратимое действие без возможности его подтвердить.
- Частичное уничтожение флоры и достижение лимита лечения при сохранившихся проблемах возвращают неполный результат с ошибкой. «Ко мне» требует непрерывно провести заданное время рядом с целью.

Проверка означает состояние в момент завершения действия. Другой персонаж или работающая машина могут изменить его позже; перед следующим зависимым действием нужны актуальные ссылки и, при необходимости, новый осмотр.

## Проверка в игре

1. Выдать план получения предмета с `ensure: "has('#ID')"`. До получения предмета следующие действия должны ждать; повторного подбора из-за проверки быть не должно.
2. Указать недостижимый результат, например заведомо большее количество предметов. После успешного действия и отдельного срока проверки должен выполниться `catch`, без повторного изготовления или расходования ресурсов.
3. Добавить хвост во время `verifying`, осмотреть план, затем попробовать вставку перед проверяемым узлом. Хвост сохраняется, вставка отклоняется, срок проверки не сбрасывается.
4. Занять фабрикатор другим ботом, остановить питание или временно лишить бота возможности двигаться. Сверить причину и количества в мониторе и наблюдении LLM.
5. Оставить долгий исправный рецепт работать. Изменение таймера и выпуск продукции должны считаться продвижением; самостоятельного повторного запуска рецепта быть не должно.
6. Во время передачи нескольких предметов переместить уже доставленный предмет из целевого слота. Финальный результат должен учитывать текущее содержимое.
7. Отменить проверяемый план, выдать приказ из меню и сменить раунд. Старое подтверждение не должно продолжить прежние шаги.
8. Удалить выбранный для разбора предмет сторонним действием до его обработки машиной. Задача должна сообщить об отсутствии подтверждённого разбора; обычный разбор, включая быстрый модовый рецепт, подтверждается нативным потреблением.

Проверено: **1068 автоматических тестов прошли**, сервер и клиент собраны для Windows/Linux/macOS, симулятор также собирается. В семи итоговых сборках нет ошибок и предупреждений компилятора. Тестовый проект сообщил о недоступности проверки уязвимостей NuGet по сети; тесты используют уже восстановленные зависимости.

Тесты включают дерево и схемы `ensure`, реальные ответы имитатора LLM через менеджер, ожидание свежих фактов без повторного действия, ближайший `catch`, сохранение проверки при редактировании, отмену и устаревшие отчёты, advisory watchdog, сериализацию наблюдений/монитора и переходы состояния нативного удаления.

Игровой прогон этой версии пока не выполнен.
