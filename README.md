# BarotraumaLLMAI: LLM-агенты для ботов Barotrauma

Серверный C#-мод для [LuaCsForBarotrauma](https://github.com/evilfactory/LuaCsForBarotrauma). Каждый бот экипажа работает как отдельный агент:

- раз в несколько секунд, а при опасности раньше, получает JSON-наблюдение о себе и подлодке;
- через tool calling просит LLM выбрать действие;
- выполняет его **штатными приказами игры**, а ходьбу, сварку, лечение и бой делает ванильный ИИ.

Боты могут переписываться друг с другом (`message_crew`; игроки слышат эти фразы по радио), вести заметки (`remember`) и говорить (`say`): по радио, если на них гарнитура, иначе вслух. Между раундами боты помнят факты, итоги прошлых раундов, отношения к людям и предпочтения игроков (локальная «база» в JSON-файлах, своя для каждой кампании).

**Полный контроль ИИ.** В командном меню есть модовый приказ «Полный контроль ИИ»: бот, получивший его, сам решает всё, может перестраивать приказы, отданные через меню, и командует остальными ИИ-ботами (`order_crew`).

**Приказы из чата.** Игрок пишет в чат обычным текстом («Механики, откачайте воду», «Анна, за мной»). Сначала LLM-диспетчер решает, кому из услышавших ботов адресован приказ: по имени, по профессии, всем или самому подходящему. Затем каждый адресат обрабатывает приказ своим LLM-вызовом вне очереди.

**Характеры экипажа.** Каждому боту можно задать характер: готовый (ветеран, новичок, трус, весельчак, педант, ворчун, герой, бунтарь, молчун, заботливый — все редактируются) и/или свой промпт с моделью поведения. Без характера учитывается черта персонажа из самой игры.

**Настройка в игре.** Окно настроек (`!llm` в чате или Ctrl+Shift+L) и чат-команды `!llm set/get/persona`. Изменения применяются сразу, без перезапуска раунда.

Поддерживаются локальные и облачные модели: любой OpenAI-совместимый API (Ollama, LM Studio, vLLM, OpenAI, OpenRouter...) и Anthropic. Подключения и лимиты настраиваются в `llm_config.json` или прямо в игре.

> **Статус:** код собирается против reference-DLL текущей LuaCs (`luacsforbarotrauma_refs.zip`, latest), логика покрыта тестами (275 шт.) и прогнана в симуляторе с мок-LLM. **В самой игре ещё не запускался.** Вызовы игры (`src/LlmAgents.Server/GameAdapter.cs`) сверены с исходниками LuaCs/Barotrauma, но поведение нужно проверить на живом сервере.

## Как это устроено

```
игровой поток (IEventUpdate)                     пул потоков
───────────────────────────                      ───────────
AgentManager.Update() каждые tickSeconds
 ├─ выполняет готовые команды ◄─────────────────────────────┐
 ├─ GameAdapter.Observe(bot) → Observation (JSON)           │
 └─ пора решать / срочно? → LlmRouter.TryReserve(слот) ───► провайдер LLM ─► tool calls
                              (лимиты, без ожидания)        │  ошибка → fallback-провайдер
```

- **Игра не блокируется.** HTTP идёт в фоне, ответ превращается в команды, которые выполняются на игровом потоке.
- **Приказы как у игрока.** `Character.SetOrder` плюс `OrderChatMessage` клиентам, ровно так сервер обрабатывает приказ из командного меню. Поэтому приказы видны в интерфейсе экипажа.
- **Фолбэк на ваниль.** Если провайдер недоступен, исчерпан лимит или пришёл мусор, бот ведёт себя как обычно. Инструмент `return_to_default` снимает приказы.
- **Лимиты.** Глобально и на каждого провайдера: параллельные запросы, запросы/мин, токены/мин, суточный бюджет. Слот резервируется синхронно. Если мест нет, бот не теряет ход и входящие сообщения, а пробует снова через `retrySeconds`.
- **Приказы игроков главнее.** Приказ, отданный игроком через командное меню, бот видит как `fixleaks (from player Daniil)` и сам его не меняет: такая попытка вернёт ошибку. Заменить его может только решение, принятое по новому приказу игрока из чата. Свой приказ бот не переотдаёт, если уже его выполняет. Свои приказы бот ставит ниже приказов игроков и не отдаёт такие, которые отменили бы приказ игрока (тот же тип приказа, другой приказ перемещения, станция, которую игрок поручил другому боту).
- **Честная очередь.** Каждый тик желающие подумать боты сортируются: сначала приказ игрока, потом тревога или входящие, потом плановые; внутри группы первым идёт тот, кто дольше ждал. Раньше при одном слоте боты в конце списка (часто ассистенты) могли не получить ни одного решения.
- **Без болтовни.** Сообщение от другого бота адресат читает при следующем решении (через половину `decisionIntervalSeconds`), а не мгновенно: раньше боты перебрасывались «Принял!» — «Спасибо!» быстрее, чем происходило что-то ещё. Промпт запрещает сообщения вида «all clear», «standing by». В чат произносится не больше `maxChatEchoPerMinute` таких фраз в минуту.
- **Агентность.** У каждого бота своя история (`historyTurns`), заметки, входящие сообщения, провайдер и доп. промпт по профессии. Сообщение будит адресата раньше срока. Число сообщений ограничено (`maxMessagesPerMinute`), чтобы боты не перекидывались «Принял!» бесконечно.
- **Планы и цели.** Один ответ модели — это план до `maxActionsPerDecision` шагов, которые выполняются по очереди. Задача (`equip`, `craft`, `deconstruct`, `treat`, `move_item`, `refuel_reactor`) и `go_to_room` завершаются до начала следующего шага, например: надеть костюм → дойти до отсека → разобрать шкафчик. Пока план выполняется, модель заново не спрашивают. Новый запрос будет, только если:
  - план выполнен (модель видит результаты всех шагов);
  - шаг провалился (остаток плана отменяется);
  - игрок отдал приказ;
  - появилась новая тревога (те, о которых бот знал при составлении плана, не считаются);
  - план идёт дольше `maxPlanSeconds`.

  Если модель спросили посреди плана, она видит оставшиеся шаги (`plan`) и может продолжить их через `keep_plan`. Ещё у бота есть **цель** (`goal`): её ставит `set_goal`, а приказ игрока становится целью автоматически. Цель показывается в каждом запросе, пока бот не отметит её выполненной, поэтому между мелкими шагами он не забывает, зачем всё это делает. `!llm status` и вкладка «Статус» показывают цель и план каждого бота. Выключить пошаговое выполнение можно через `"sequentialActions": false`: тогда все действия ответа выполняются сразу.
- **Разовые приказы заканчиваются.**
  - «Ко мне» / «сюда» выполняется инструментом `come_to`: бот идёт туда, где игрок находится сейчас, и догоняет, если тот ушёл. Рядом с игроком он стоит `comeToWaitSeconds` (90 с), после чего приказ считается выполненным, и бот возвращается к своим обязанностям. Раньше `go_to_room` привязывал бота к отсеку, откуда игрок уже ушёл, до конца раунда.
  - Модель знает, что разовый приказ («скрафти», «принеси», «разбери», «подойди») по выполнении закрывается.
  - Старые приказы в заметках показаны с возрастом («(4 min ago) Player order: …»).
  - Цель старше `goalTimeoutMinutes` (8 мин) снимается автоматически.
- **Без лишних запросов и болтовни.** Если плановые решения бота ничего не меняют («жду», «уже делаю»), он думает всё реже: 10 → 20 → 40 → 60 с. Приказ, сообщение, тревога или результат задачи сразу возвращают обычный темп. Фразы вроде «на месте, жду указаний» модели запрещены, если игрок о них не спрашивал.
- **Приказы из чата не теряются.** Если для разбора приказа нет свободного запроса к модели дольше `chat.dispatchWaitSeconds` (6 с), приказ получают боты, названные в тексте по имени, а если имён нет — все, кто его слышал. Сообщения, начинающиеся с `!` или `/` (команды других модов), экипажу не передаются. Команды мода понимаются и в русской раскладке: `!ддь ыефегы` = `!llm status`.
- **Модели без tool calling.** Если модель пишет вызов текстом (JSON или «Gemma-стиль» `say{text:<|"|>…<|"|>}`, `remember,"note":"…"`, голое `wait`, имена ванильных приказов вроде `repairsystems`), он всё равно распознаётся. Для таких моделей лучше включить у провайдера `"toolMode": "prompt"`: инструменты описываются прямо в промпте, а модель отвечает строгим JSON.
- **Упавший провайдер не мешает.** После 401/403/404 провайдер пропускается 5 минут (`providerAuthCooldownSeconds`), после 429, ошибок 5xx и таймаутов он ставится на нарастающую паузу (5 с, 10 с, … до 2 мин). На это время боты сразу идут к `fallbackProvider` в общей очереди. В лог пишется одна строка с причиной, а не ошибка каждые 10 секунд.

### Инструменты агента

| Инструмент | Что делает в игре |
|---|---|
| `go_to_room(room, priority?)` | приказ `wait` с позицией в отсеке: дойти и стоять |
| `follow(target, priority?)` | приказ `follow` за членом экипажа |
| `fix_leaks`, `repair_systems`, `extinguish_fires`, `fight_intruders`, `rescue_injured`, `clean_up`, `wait` (все с `priority?`) | соответствующие ванильные приказы |
| `operate(role, option?, priority?)` | `reactor` (`powerup`/`shutdown`), `navigation`, `weapons`, `pumps` (`pumpout`/`pumpin`) |
| `set_order_priority(order, priority)` | поменять приоритет своего приказа (1–3) или снять его (0) |
| `return_to_default` | `dismissed`: снять приказы, вернуть ванильный ИИ |
| `say(text)` | реплика: по радио, если надета рабочая гарнитура, иначе вслух (как у ванильных ботов; `global.speechChannel`) |
| `message_crew(to, text)` | сообщение боту по имени, всем ботам профессии (`mechanic`) или всем (`all`). Игроки тоже его слышат: бот произносит `[→ Bob] текст`. Если адресат — живой игрок, бот просто говорит ему по радио: «Имя, текст» |
| `remember(note, long_term?)` | заметка в память бота; с `long_term=true` сохраняется на диск и видна в следующих раундах |
| `forget(text)` | удалить устаревший долговременный факт |
| `note_relationship(person, feeling, note)` | отношение к человеку: `trust`, `like`, `neutral`, `dislike`, `distrust` + причина. Хранится между раундами |
| `note_preference(player, preference)` | предпочтение игрока («короткие доклады», «реактор на 50%»). Общее для всех ботов |
| `order_crew(to, order)` | **только под полным контролем ИИ:** обязательный приказ другим ИИ-ботам |
| `equip(item)` | взять предмет из шкафа или с пола и надеть или взять в руки: водолазный костюм, оружие, сварку, гарнитуру |
| `refuel_reactor()` | принести топливный стержень и загрузить в реактор, отработанный стержень вынимается. Ванильные боты делают это только при достаточном навыке |
| `craft(item, amount, salvage?)` | собрать ингредиенты в фабрикатор и запустить изготовление (по одной штуке за цикл). Если материалов нет, ответ говорит, какой хлам на борту их даёт; с `salvage=true` бот сначала сам разбирает этот хлам в деконструкторе, потом крафтит |
| `deconstruct(item, from?)` | отнести предмет в деконструктор, дождаться разборки и сообщить, что получилось. С `from` (контейнер или отсек, например «шкаф в Электрика [h140]») берутся только предметы оттуда; `item="all"` = всё, что там можно разобрать (до 12 за раз) |
| `treat(target, item?)` | лечение. Без `item` берётся самое дешёвое из достаточно подходящих средств (из тех, что дают не меньше половины эффекта лучшего), так что дорогие препараты не тратятся на царапины. С `item` используется указанный предмет |
| `unequip(item)` | снять надетое или убрать из рук в свой инвентарь |
| `drop(item)` | бросить предмет на пол |
| `move_item(item, to)` | отнести предмет: в контейнер (`to` = «шкаф», «medical cabinet»...), в отсек (`to` = id отсека) или отдать члену экипажа (`to` = имя) |
| `keep_gear(on)` | заблокировать водолазное снаряжение: бот не снимет его сам даже в сухом отсеке |
| `inspect(kind, query)` | справка, ответ приходит в следующем ходу: `patient` (травмы и подходящие лекарства; без query — все раненые), `items` (где лежат предметы), `recipes` (что умеют фабрикаторы этой подлодки и что можно сделать прямо сейчас; query — фильтр), `recipe` (рецепт: что есть, чего не хватает и откуда взять), `salvage` (какие предметы на борту разбираются на нужный материал / на что разбирается предмет / весь хлам на борту) |

### Крафт и разборка

Раньше боты не знали, что можно сделать и из чего, и придумывали названия наугад. Теперь:

- **Список рецептов.** `inspect(kind='recipes')` выдаёт рецепты фабрикаторов этой подлодки. Сначала идёт то, что можно сделать из имеющегося прямо сейчас, затем то, чему не хватает материалов (с указанием, чего именно). Рецепты, закрытые талантами, которых ни у кого нет, не показываются. Фильтр работает по слову или категории: `medical`, `ammo`, название материала. Промпт велит не угадывать названия, а брать их из этого списка.
- **Названия на двух языках.** Предметы показываются как «Топливный стержень (Fuel Rod) [fuelrod]», и поиск понимает русское, английское название и идентификатор. Модель может писать «fuel rod» в русской игре, и это работает для всех инструментов, не только для крафта.
- **Подсказки по материалам.** Если ингредиентов нет, ответ `craft` и `inspect(kind='recipe')` говорят, какой хлам на борту их даёт («Железо x2: deconstruct Ржавая труба (gives 1, 3 aboard)») или из чего этот материал можно скрафтить. При ошибке в названии предлагаются похожие рецепты.
- **Разбор хлама.** `inspect(kind='salvage', query='steel')` показывает, что на борту разбирается на сталь. С query-предметом показывает, на что разберётся этот предмет, без query — весь хлам.
- **Разборка и крафт одной задачей.** `craft(item, salvage=true)` подбирает самый дешёвый хлам, разбирает его по одному предмету, ждёт результат и крафтит. Мод никогда не разбирает лекарства, оружие, водолазное снаряжение, топливные стержни, ID-карты, надетое, предметы с содержимым и сами ингредиенты рецепта. Разбор со случайным результатом идёт в последнюю очередь.
- **Только свободные запасы.** В запасы не входят предметы, заряженные в работающие механизмы: стержни в реакторе, боеприпасы в турели, батареи. Выход фабрикатора и деконструктора входит.
- **Ожидание разборки.** `deconstruct` теперь ждёт, пока деконструктор действительно разберёт предмет, и сообщает, что получилось. Если машина остановилась (нет питания), бот получает ошибку.

### Водолазное снаряжение в бою

Ванильные боты снимают костюм, как только в их отсеке сухо (`HumanAIController.UnequipUnnecessaryItems`). В бою это кончается плохо: враг пробивает корпус, и бот не успевает добежать до костюма. Мод ставит Harmony-патч на этот метод (`src/LlmAgents.Server/GearLock.cs`). Пока снаряжение бота заблокировано, костюм не снимается. Блокировка бывает двух видов:
- **вручную:** бот вызвал `keep_gear(true)`, например по приказу «всем надеть костюмы»;
- **автоматически:** подлодка в опасности — монстр ближе `dangerMonsterRadiusMeters` (80 м) к подлодке, есть пробоины, вода на борту или враг внутри (`keepDivingGearInDanger`, по умолчанию включено).

Исключение: если боту не хватает воздуха (например, в костюме пустой баллон), ванильная логика работает как обычно и может снять костюм, чтобы бот не задохнулся. В наблюдении бот видит `equipped` (что надето), `inventory` (что несёт) и `gear`, например `Водолазный костюм on (oxygen 80%); DANGER: gear locked automatically`. Если опасность есть, а костюма на боте нет, это считается тревогой: бот думает сразу и надевает костюм. Снять заблокированный костюм бот сам не может (`unequip`/`drop` вернут ошибку), только по приказу игрока.

`equip`, `refuel_reactor`, `craft`, `deconstruct`, `treat` и `move_item` — многошаговые сценарии (`src/LlmAgents.Server/BotTasks.cs`). Каждый шаг выдаётся боту как ванильная цель (взять предмет, дойти, положить в контейнер). Последний шаг, которого ванильные боты сами не делают, выполняет мод: применяет выбранное лекарство, запускает фабрикатор. Ход сценария виден боту в `currentTask`, итог приходит в `lastActionResults`, и бот сразу думает снова.

Список можно сузить через `bots.allowedTools`.

### Приоритеты приказов

Как в ванильной игре: у бота до трёх приказов с приоритетом 1–3, где 3 — главный. Бот работает над самым приоритетным приказом, у которого есть работа, а младшие заполняют паузы. Например, `fix_leaks` [p3] + `operate reactor` [p2]: пока есть пробоины, бот варит, иначе стоит у реактора. В `currentOrder` бот видит приказы так: `fixleaks [p3] (from player Daniil), operatereactor:powerup [p2]`.

- У всех приказов-инструментов есть необязательный `priority` (по умолчанию 3, можно `high`/`normal`/`low`). Новый приказ с приоритетом p сдвигает на ступень вниз приказы с приоритетом p и ниже; четвёртый выпадает. Так ведёт себя и командное меню игры.
- `set_order_priority(order, priority)` переставляет приказы или снимает приказ (0), когда обстановка изменилась.
- Игрок может задать порядок в чате: «Механики, сначала тушите пожар, потом течи» → `extinguish_fires` [p3], `fix_leaks` [p2].
- Без слова игрока свои приказы бот ставит только ниже приказов игроков (приоритет понижается автоматически, в ответе пишется почему) и не меняет приоритеты приказов игроков.
- Мод больше не снимает прошлый свой приказ при новом: приказы складываются по приоритетам.

### Полный контроль ИИ (модовый приказ)

В командном меню, в категории «Перемещение», появляется приказ **«Полный контроль ИИ»** (иконка с микросхемой; `Content/Orders.xml`). Его можно отдать боту из списка экипажа или колеса приказов.

- **Выдать:** отдать приказ боту. **Забрать:** отдать его же ещё раз или снять с бота все приказы («Отставить»). Бот подтверждает голосом.
- Под контролем бот:
  - думает чаще (`bots.controlDecisionIntervalSeconds`, 6 с) и действует на опережение по отдельному блоку инструкций;
  - может заменять и переставлять приказы, отданные ему игроками через меню;
  - получает инструмент `order_crew`: обязательные приказы другим ИИ-ботам. Они выполняют их как приказ игрока, но приказ живого игрока важнее, и перебивать приказы, которые игроки дали им через меню, такие приказы не дают. Приказ произносится в эфир (`[→ Олег] …`).
- Приказы живых игроков в чате по-прежнему главнее планов бота. Заблокированный при опасности водолазный костюм снять тоже можно только по слову игрока.
- Контроль хранится в памяти бота и переживает конец раунда, пока игрок его не заберёт.
- `bots.autonomy`: `"always"` (по умолчанию) — все боты думают сами, как раньше; `"order"` — без полного контроля бот обращается к LLM только по приказам из чата, сообщениям и итогам своих задач, остальное делает ванильный ИИ. Так полный контроль включается только тем ботам, кому он нужен, и экономит запросы.

Как это сделано: у игры нет цели ИИ для такого приказа, поэтому Harmony-префикс на `Character.SetOrder` (`src/LlmAgents.Server/ControlOrder.cs`) перехватывает его до ванильной логики, а `GameServer.SendOrderChatMessage` не рассылает его клиентам. Иначе ванильный клиент написал бы в консоль «Failed to create an objective» и открыл её. Из-за этого значок приказа не появляется в списке приказов бота у клиентов: о передаче контроля бот сообщает голосом.

### Долговременная память

Память хранится в `memory/<кампания>.json` в папке мода (`memory.folder`): отдельный файл на каждое сохранение кампании (`campaign_<имя сохранения>.json`), всё вне кампаний пишется в `default.json`. Боты различаются по имени персонажа. Файл обычный JSON с кириллицей, его можно читать и править руками (лучше между раундами). Запись атомарная: временный файл и замена. Испорченный файл не теряется: он сохраняется как `.bad`, и память начинается заново.

| Что | Откуда | Где видит бот |
|---|---|---|
| факты (`facts`) | `remember(note, long_term=true)`, `forget` | `memory.facts` |
| журнал раундов (`journal`) | в конце раунда каждый бот одним LLM-вызовом пишет 1–2 фразы об итогах раунда; если модель недоступна, сохраняется краткая выжимка событий | `memory.pastRounds` (последние `journalInPrompt`) |
| отношения (`relationships`) | `note_relationship` | `memory.relationships`, сначала про тех, кто на борту |
| предпочтения игроков (`players`) | `note_preference`, общие для всего ИИ-экипажа | `memory.playerPreferences`, только про игроков на борту |
| полный контроль ИИ | модовый приказ | `control` |

Итог раунда собирается из журнала событий раунда: приказы, итоги задач, сообщения, передача контроля. Модель для итогов задаётся в `memory.summaryProvider`. Если все слоты заняты, итог ждёт свободный слот до 45 секунд. Отключить память целиком: `"memory": { "enabled": false }`, тогда инструменты памяти не предлагаются.

## Диагностика: `!llm status`

Команда `!llm status` (или вкладка «Статус» в окне настроек) отвечает одним сообщением:
- версия мода. Так сразу видно, какая сборка загружена на сервере;
- работают ли патчи и функции: блокировка костюмов, приказ «Полный контроль ИИ», приказы из чата, окно настроек. Что не работает, помечается `PROBLEMS` с причиной;
- сколько запросов сделано сегодня;
- по каждой модели: число ответов и ошибок, среднее время ответа, загрузка, пауза после ошибок, последняя ошибка;
- по каждому боту: его приказы, текущая задача, последнее решение и как давно оно было («думает сейчас», если ждёт ответа), последняя ошибка.

`!llm ai <имя> off` отдаёт конкретного бота обычному ИИ игры, `!llm ai <имя> on` возвращает его под LLM. Это же можно сделать переключателем во вкладке «Статус». Список хранится в `bots.disabledCharacters`.

## Настройка в игре

Настраивать могут владелец сервера (хост) и игроки с правом «Управление настройками» (ManageSettings). Остальным команды отвечают «Нет прав».

**Окно настроек.** Откройте его командой `!llm` в чате или сочетанием **Ctrl+Shift+L**. Окно работает и в лобби, и во время раунда. Для него нужна клиентская часть мода (`bin/Client/.../LlmAgentsClient.dll`), а она загружается только там, где установлена LuaCs с включённым C#. У хоста LuaCs и так стоит, остальным игрокам окно не нужно. Вкладки:

| Вкладка | Что там |
|---|---|
| Статус | версия, что работает, модели, по каждому боту: приказы, задача, последнее решение, ошибки; переключатель «Только ванильный ИИ» |
| Общее | вкл/выкл мода, самостоятельность (`autonomy`), язык речи ботов, интервалы решений, число действий и сообщений, канал речи, костюмы при опасности, лог |
| Экипаж | все ИИ-боты на борту (с профессией, чертой из игры и отметкой полного контроля) и сохранённые персонажи: характер, свой промпт, своя модель, вкл/выкл |
| Характеры | готовые характеры (название и промпт), удаление, создание нового |
| Профессии | для каждой профессии игры: модель, «ванильный ИИ», промпт профессии (`extraPromptByJob`) |
| Модели | модель по умолчанию и запасная; у каждого провайдера модель, адрес, переменная с ключом, режим инструментов, температура, лимиты |
| Лимиты | общие лимиты запросов и паузы провайдеров |
| Чат и память | приказы из чата, префикс, диспетчер; долговременная память и итоги раундов |

Кнопка «Обновить» заново загружает значения и статус. Правки копятся до кнопки «Применить», которая отправляет их на сервер. Сервер проверяет весь набор правок разом: если хоть одна неверная, ничего не меняется и в строке состояния видна причина. Затем он сохраняет `llm_config.json` / `personas.json` и сразу применяет. Агенты при этом не перезапускаются: история, задачи и контроль сохраняются. Если поменялись провайдеры или лимиты, пересоздаётся маршрутизатор запросов (идущие запросы спокойно завершаются), и счётчики «запросов в минуту/сутки» начинаются заново. «Перечитать файлы» подхватывает правки, сделанные в файлах руками.

**API-ключи в игре не редактируются**: трафик игры не шифруется. Ключ задаётся переменной окружения на сервере, а в окне указывается только её имя (`apiKeyEnv`) и видно, задан ли ключ.

**Чат-команды** (работают без клиентской части; отвечает сервер личным сообщением, другие игроки команду не видят, и ботами она не воспринимается как приказ). Вместо `!llm` можно писать `!ии` или `!ai`:

```
!llm                                   справка (и открыть окно, если есть клиентская часть)
!llm list [вкладка или начало ключа]   ключи и значения, например: !llm list global
!llm get global.decisionIntervalSeconds
!llm set global.decisionIntervalSeconds 8      можно коротко: !llm set decisionIntervalSeconds 8
!llm set bots.autonomy order                   варианты списков — по id или по подписи («По приказу»)
!llm set providers.local.model gemma3:27b
!llm set bots.providerByJob.captain cloud      пусто/«-» = по умолчанию
!llm persona Иван                      показать характер (имя можно не полностью и латиницей: ivan)
!llm persona Иван preset veteran
!llm persona "Ivan Petrov" prompt Бывший шахтёр, говорит медленно и обстоятельно.
!llm persona Иван provider cloud | on | off | clear
!llm presets                            список характеров
!llm preset Пират Говорит как старый пират, ругается «тысяча чертей»   создать (id: pirat) или изменить
!llm preset pirat delete
!llm reload                             перечитать файлы
```

Имена с пробелами берутся в кавычки ("…" или «…»).

**Ограничения.** При сохранении из игры комментарии в `llm_config.json` пропадают: файл переписывается как обычный JSON, а неизвестные ключи сохраняются. Добавить нового провайдера можно только в файле.

## Характеры экипажа

Характеры лежат в `personas.json` в папке мода. Файл создаётся при первом запуске с готовыми характерами, его можно править в игре или руками:

```jsonc
{
  "presets": {
    "veteran": { "name": "Ветеран", "prompt": "Ты ветеран, переживший десятки погружений. Спокоен, говоришь мало и по делу..." }
    // rookie, coward, joker, pedant, grumpy, hero, rebel, silent, caring
  },
  "characters": {
    "Ivan Petrov": { "enabled": true, "preset": "veteran", "prompt": "Бывший шахтёр, любит рассказывать про шахты.", "provider": "cloud" }
  }
}
```

- Персонаж определяется по имени, как и долговременная память.
- В системный промпт бота идёт блок `YOUR CHARACTER`: сначала текст характера, затем свой промпт. Характер влияет на то, как бот говорит, что замечает и какое из разумных действий выбирает. Приказы игроков и выживание остаются в силе, **если текст характера прямо не говорит иное**. Можно сделать бота, который саботирует приказы, но это нужно написать явно.
- `provider` — своя модель для этого персонажа (например, капитану облачную, остальным локальную). Это важнее `providerByJob`.
- Без характера бот получает черту из игры (`Вспыльчивый`, `Ленивый`…), если включено `bots.useGamePersonality`.
- `bots.speechLanguage` (например, `Russian`) задаёт язык реплик всех ботов.
- Промпт профессии (`extraPromptByJob`, вкладка «Профессии») добавляется отдельно, до характера. Удобно разделять: в профессии — обязанности, в характере — личность.

## Приказы из чата

```
игрок пишет в чат ──► IEventChatMessage (ChatListener)
                       └─ кто услышал: в радиусе голоса или оба с гарнитурами (функции игры)
                    ──► диспетчер (LLM, инструмент route_message): кому адресовано?
                          «Олег, …» → Олег; «механики, …» → все механики; «механик, …» → один, самый подходящий;
                          «все, …» → все услышавшие; болтовня → никому
                    ──► каждый адресат: playerOrders в наблюдении → свой LLM-вызов сразу, вне очереди
```

- Приказ бот видит дважды: обычным текстом **перед** JSON-наблюдением («NEW ORDER - carry out now…») и первым полем `playerOrders` внутри него. Маленькие локальные модели иначе пропускают приказ в длинном наблюдении.
- К приказу добавляются комната отправителя, пояснение «'me' = <отправитель>» и подсказка для частых фраз. Например, «ВСЕ ЗА МНОЙ!» → `Hint: probably follow(target="<отправитель>")`, «ко мне» → `go_to_room` в его комнату, «разберите…» → `deconstruct(item="all", from=…)`. Подсказки покрывают только однозначные фразы (русские и английские), решает всё равно модель (`OrderHints.cs`).
- Диспетчер: команда во множественном числе без адресата («разберите», «идите») уходит всем или всем подходящим по профессии; приветствие всем («привет всем») — одному (капитану), чтобы не отвечал хором весь экипаж.
- Если сообщение услышал только один бот, диспетчер не вызывается.
- Если диспетчер недоступен, приказ получают боты, чьи имена упомянуты в тексте; кириллица и латиница сравниваются через транслитерацию. Если имён нет, приказ получают все услышавшие, и каждый решает сам, ему ли он.
- Адресат видит, кому ещё ушёл приказ (`also sent to`), и может поделить работу через `message_crew`. Приказ сохраняется в заметках бота.
- В LuaCs есть ошибка: событие чата не доходит до сервиса событий плагина, если на основном сервисе у него нет своих подписчиков. Поэтому мод подписывается на чат напрямую на основном сервисе LuaCs.
- LuaCs не сообщает, писал ли игрок в радио-канал. Поэтому если на игроке гарнитура, считается, что его слышат по радио.
- Настройки в разделе `chat`: `prefix` (например, `"!"`, чтобы приказами считались только такие сообщения), отдельный `provider` для диспетчера, `allowSpectators`.

## Структура

```
Content/                     пакет мода: filelist.xml, ModConfig.xml, llm_config.json,
                             Orders.xml + Texts/ + Images/ (приказ «Полный контроль ИИ»)
src/LlmAgents.Core/          логика без зависимостей от игры: провайдеры, лимиты, агенты, инструменты, память (Memory/)
src/LlmAgents.Core/          … Personas/ (характеры), Settings/ (схема настроек, правка конфига, чат-команды, протокол окна)
src/LlmAgents.Server/        серверный плагин LuaCs (Plugin.cs) + GameAdapter.cs, единственное место с типами игры;
                             SettingsBridge.cs — сетевые сообщения окна и команды !llm
src/LlmAgents.Client/        необязательный клиентский плагин: окно настроек (SettingsWindow.cs)
tests/LlmAgents.Tests/       xUnit-тесты Core
tools/LlmAgents.Sim/         симулятор подлодки: настоящий агентный код без игры
tools/mock_llm_server.py     мок OpenAI-совместимого сервера
tools/get-refs.*             скачать reference-DLL игры в Refs/
tools/package.*              собрать мод под Windows/Linux/OSX в dist/LlmAgents (и выложить в LocalMods)
```

`LlmAgents.Server` компилирует исходники Core в себя, поэтому серверная часть — одна DLL. Клиентская `LlmAgentsClient.dll` берёт из Core только файл протокола (`SettingsProtocol.cs`). `package.*` собирает обе под три платформы.

## Сборка

Нужен .NET 8 SDK.

```powershell
.\tools\get-refs.ps1                       # один раз: reference-DLL в Refs\ (Linux/macOS: tools/get-refs.sh)
dotnet test tests\LlmAgents.Tests          # тесты
.\tools\package.ps1                        # мод → dist\LlmAgents
.\tools\package.ps1 -LocalMods "C:\Program Files (x86)\Steam\steamapps\common\Barotrauma\LocalMods"
```

При повторной выкладке `llm_config.json`, который уже лежит в `LocalMods`, не затирается.

CI (`.github/workflows/build.yml`) собирает и тестирует только часть без игры (Core, тесты, симулятор): reference-DLL игры в репозиторий не кладутся, поэтому сам плагин собирается локально.

Reference-DLL должны соответствовать версии LuaCs на сервере. Если LuaCs обновится и что-то сломается, перекачайте refs и пересоберите.

## Установка и запуск

1. Установите LuaCsForBarotrauma и включите C# (LuaCs Settings → Enable CSharp, или `EnableCsScripting="true"` в `LuaCsConfig.xml`). На выделенном сервере LuaCs ставится вручную (server patch).
2. Положите `dist/LlmAgents` в `LocalMods` хоста или сервера и включите мод.
3. Мод **серверный**: решения ботов принимает сервер, клиентам LuaCs не нужен. Но в пакете теперь есть контент (приказ «Полный контроль ИИ», его иконка и тексты), поэтому при подключении клиенты скачивают мод, как любой другой мод сервера. Проверьте на практике, не предложит ли LuaCs клиентам включить C#.
4. Настройте `llm_config.json` в папке мода или прямо в игре (`!llm`). Файл перечитывается в начале каждого раунда. Характеры лежат в `personas.json`.
5. Лог всех запросов и ответов пишется в `llm_agents.log` в папке мода. В консоль сервера попадают только предупреждения и ошибки.

  "global": {
    "maxConcurrentRequests": 3,      // одновременно на весь сервер

- **Новые настройки при обновлении.** Если в вашем `llm_config.json` нет каких-то ключей (их добавила новая версия), мод при запуске сам дописывает их со значениями по умолчанию. Ваши значения не трогаются, копия старого файла сохраняется в `llm_config.json.bak`, а в консоли сервера пишется список добавленного.
- **`compactObservation`** (включено по умолчанию). Запрос к модели становится короче:
  - наблюдение без пустых полей; экипаж и угрозы — одной строкой на каждого; отсеки — списком id плюс отдельный `roomAlerts` с отсеками, где вода или огонь (на реальном наблюдении из игры около 4,0 → 2,8 КБ);
  - главное: прошлые ходы в истории хранятся одной строкой («где был, какой приказ, что пришло, что получилось»), а не целым старым наблюдением. При `historyTurns: 6` запрос уменьшается примерно в 2,5 раза.
  Маленькие локальные модели от этого заметно быстрее отвечают и реже теряют приказы в длинном тексте. Выключать стоит, только если модели не хватает подробностей прошлых ходов.
- `toolMode`: `"native"` использует tool calling самого API (облако, Qwen в Ollama и т.п.), `"prompt"` описывает инструменты в промпте и ждёт ответа JSON. Ставьте `"prompt"`, если в логе видно, что ответы модели — текст, а действий нет. Ollama в этом режиме получает `response_format: json_object`; если сервер его не поддерживает (LM Studio), мод сам повторит запрос без этого поля.
- `type`: `"ollama"` — родной API Ollama (`/api/chat`, `baseUrl` можно указывать с `/v1` и без); `"openai"` — любой OpenAI-совместимый сервер; `"anthropic"` — Claude.
- `thinking` («Размышления модели» во вкладке «Модели»): `"off"` — модель отвечает сразу, без рассуждений (Ollama получает `think: false`, OpenAI-совместимым серверам в системный промпт добавляется `/no_think` для Qwen3); `"on"` — включить; `"auto"` — как решит модель/сервер. Для ботов почти всегда лучше `"off"`: рассуждения в разы замедляют ответ, а качество действий растёт мало. Текст `<think>…</think>` из ответа в любом случае вырезается.
- `contextLength` (только `ollama`): размер контекста (`num_ctx`). По умолчанию Ollama даёт маленькое окно и молча обрезает длинный промпт — бот может не увидеть приказ. 8192–16384 обычно хватает; больше — больше видеопамяти. `0` — значение сервера.
- `maxOutputTokens`: план из нескольких шагов с русским текстом занимает 500–900 токенов, поэтому по умолчанию стоит 800. Если в логе появляется `reply from '…' was cut off at maxOutputTokens`, значит ответ обрезался и часть действий потерялась: увеличьте значение. У рассуждающих моделей лимит съедают рассуждения, поэтому для них лучше выключить размышления.
- `extraBody`: поля, которые добавляются в каждый запрос, для особых переключателей конкретного сервера. Например, `{"reasoning": {"enabled": false}}` для OpenRouter и похожих агрегаторов или `{"chat_template_kwargs": {"enable_thinking": false}}` для vLLM с Qwen3.
- `proxy`: прокси только для этого провайдера, например `"http://127.0.0.1:10809"` или `"socks5://127.0.0.1:1080"`. Пригодится, если API недоступен напрямую. Пусто — используются системные настройки прокси.
- `connectTimeoutSeconds` (по умолчанию 8): если сервер недоступен, попытка соединения обрывается через столько секунд и запрос сразу уходит запасному провайдеру. Без этого запрос висел около 20 секунд.
- `keepAliveMinutes` (только `ollama`): сколько держать модель в памяти после запроса, чтобы она не выгружалась между ходами. `0` — значение сервера.
- OpenAI, OpenRouter и т.п.: `"type": "openai"` и их `baseUrl` (например, `https://api.openai.com/v1`).
- LM Studio: `http://127.0.0.1:1234/v1`.

**Какую локальную модель взять.** Нужна модель, которая уверенно вызывает инструменты и держит длинный промпт.
- 8 ГБ видеопамяти (вместе с игрой): `qwen3:8b` (Q4_K_M, ~5 ГБ с контекстом 12k), `thinking: off`. Если игра начинает подтормаживать — `qwen3:4b` или `contextLength: 8192`.
- 12–16 ГБ: `qwen3:14b`; 24 ГБ: `qwen3:32b` или `qwen3:30b-a3b`.
- Мало видеопамяти, но много ОЗУ (32 ГБ+): `qwen3:30b-a3b` (MoE) частично на процессоре — отвечает терпимо, но первый ответ долгий.
- Ollama можно запустить на другом ПК в сети: `"baseUrl": "http://192.168.x.x:11434"` (на том ПК `OLLAMA_HOST=0.0.0.0`).
- Смешанный вариант: локальная модель для рядовых ботов, облачная (`providerByJob`, персональный провайдер в «Характерах», `chat.provider`) — для капитана, бота с полным контролем и разбора приказов из чата.
- Ключи лучше задавать через `apiKeyEnv` (переменную окружения сервера), а не в файле.

## Проверка без игры

```bash
python3 tools/mock_llm_server.py                         # мок на :11434 (или запустите Ollama)
dotnet run --project tools/LlmAgents.Sim -- --seconds 60 --speed 3
dotnet run --project tools/LlmAgents.Sim -- --provider cloud   # тот же сценарий на облачной модели
```

Симулятор гоняет пятерых ботов, среди них два механика, по сценарию: пробоина, пожар, краулер на борту. В сценарий входят приказы из чата: «Механики, откачайте воду насосами», «Анна, иди в медотсек», «Всем надеть водолазные костюмы, идёт бой», «Анна, вылечи Макса, только бинтами», «Ольга, перезаряди реактор», «Механики, приоритет: сначала тушить пожар, потом течи». На 50-й секунде игрок отдаёт капитану «Полный контроль ИИ». В конце каждый бот пишет итог раунда в память (`sim_memory/sim.json`, папку можно сменить через `--memory`). При повторном запуске видно, что память и контроль сохранились. Характеры берутся из `sim_memory/personas.json` (при первом запуске там создаются примеры). Пока симулятор работает, свои приказы можно печатать прямо в консоль. Строки с `!llm` выполняются как чат-команды настроек (в симуляторе они меняют копию конфига в памяти, файл не трогают), их можно подать и через pipe: `echo "!llm persona Olga preset pedant" | dotnet run --project tools/LlmAgents.Sim`. Симулятор выводит решения, реплики и итог. Сценарий удобен для подбора промптов, модели и лимитов.

## Разбор лога

- `[Бот] -> провайдер: {...}`: запрос, то есть наблюдение бота.
- `[Бот] <- провайдер: tool(args)  [raw: …]`: распознанные вызовы и сырой ответ модели (`logRawReplies`).
- `[Бот] tool(args) -> ok …` / `-> error: …`: что реально выполнилось в игре. **Если таких строк нет, действия не выполняются.**
- `reply had no recognizable tool call`: модель ответила текстом без вызовов. Включите `"toolMode": "prompt"` для этого провайдера.
- `provider 'X' paused for Ns: HTTP 403 …`: доступ запрещён. У Anthropic и OpenAI так выглядит запрос из неподдерживаемого региона; нужен VPN/прокси на сервере или другой провайдер (например, OpenRouter). 401 означает неверный или отсутствующий ключ, 404 — неверный `baseUrl` или имя модели.

## Что проверить в игре первым делом

- Плагин загрузился: в консоли сервера есть `[LlmAgents] loaded from ...`.
- Боты получают приказы, иконки приказов видны клиентам, `say` слышно по радио.
- Приказ в чат («Механики, …», «<имя>, …») доходит только до нужных ботов: в логе видны строки `chat from`, `dispatch <-` и `order from`.
- Приказ через командное меню бот не перебивает своими приказами (в логе `error: you are carrying out … ordered by player`).
- Блокировка костюма: в бою или при пробоине боты не снимают костюм; в консоли сервера не должно быть `diving gear lock disabled`.
- Сценарии: в логе `task '…' ok: …` или `failed: …`. Больше всего непроверенных мест в `BotTasks.cs`: запуск фабрикатора, `ApplyTreatment` и загрузка стержня через `AIObjectiveContainItem`.
- `go_to_room` (приказ `wait` с позицией), `follow` (цель берётся из `orderGiver`), `operate reactor` и `pumps`.
- Нет ли `MethodAccessException`: доступ к internal-членам игры идёт через `IgnoresAccessChecksTo` (`src/LlmAgents.Server/AccessChecks.cs`).
- Приказ «Полный контроль ИИ» есть в командном меню у клиента (категория «Перемещение»), бот подтверждает его голосом, в логе `full AI control given by …`. В консоли клиента не должно быть «Failed to create an objective», а в консоли сервера — `'Full AI control' order disabled`.
- Приоритеты: у бота в интерфейсе экипажа видно несколько приказов в правильном порядке; бот не сбивает приказ игрока своим.
- Память: после конца раунда в `memory/` появляется файл кампании, в логе строки `journal: …`. В новом раунде в наблюдении бота есть `memory`.
- Фразы `message_crew` слышны игрокам (`[→ имя] …`).
- Настройка в игре: `!llm` у хоста открывает окно (в консоли сервера нет `in-game settings window disabled`), «Применить» меняет значения и сохраняет файлы; у игрока без прав ответ «Нет прав». Без клиентской части `!llm list` и `!llm set` отвечают текстом. Проверить, что выпадающие списки не обрезаются в прокручиваемом окне.
- Характеры: после `!llm persona <имя> preset joker` бот в следующих репликах шутит; в логе при создании агента видно `(persona)`.
- Нагрузка: `Observe()` проходит по отсекам, пробоинам и персонажам не чаще раза в `urgencyCheckSeconds` на бота.
